# ICUH Platform API — 개선 실행 계획 (plan.md)

> [spec.md](./spec.md)에서 도출한 개선 포인트(S1~S18)를 **위험도·의존성·효과**를 고려해
> 5개 Phase로 묶었습니다. 위 Phase일수록 저위험·고확실성, 아래로 갈수록 구조적·전사적입니다.
> 각 Phase는 독립적으로 머지 가능하도록 설계했습니다.

---

## Phase 0 — Quick Wins (정리·일관화)
**목표:** 동작 변화 없이 코드 위생을 끌어올린다. 리뷰 부담이 작아 가장 먼저 머지.

| 작업 | spec | 비고 |
|------|------|------|
| `danName` → `damName` 오타 수정 | S1 | 단순 치환 |
| 포맷/미사용 import/자투리 공백 정리 | S2 | IDE 자동 정리 + 점검 |
| 조회 서비스 전체에 `@Transactional(readOnly=true)` 적용 | S3 | FreshFood/HydroPower 추가 |

**완료 기준:** 빌드·기존 테스트 통과, 동작 동일. 단일 PR.

---

## Phase 1 — API 계약 일관성 (Validation · Naming · Error)
**목표:** API 입력 검증과 응답 규약을 도메인 간 동일하게 맞춘다.

| 작업 | spec | 비고 |
|------|------|------|
| 모든 요청 DTO에 `@NotBlank`/`@Pattern` 검증 통일 | S4 | FreshFoodIndexRequest를 기준 패턴으로 |
| DTO 네이밍 컨벤션 통일(`~Request`/`~Response`) | S5 | 클래스/패키지 리네이밍, 광범위 diff |
| `ErrorType` 세분화(도메인·공통 케이스 추가) | S6 | 응답 코드 명확화 |
| 분류 임계값·indicator color 상수/enum화 | S7 | 도메인 VO 내부로 수렴 |

**완료 기준:** `.http` 케이스로 검증 실패/성공 응답 형식 확인. 네이밍 변경은 별도 커밋 분리.
**의존성:** S5 리네이밍은 Phase 2 이전에 끝내면 매핑 이전 작업이 깔끔해짐.

---

## Phase 2 — 서비스 슬림화 & 쿼리 정리 (구조 리팩터링)
**목표:** 서비스의 매핑 보일러플레이트를 걷어내고 조회 책임만 남긴다.

| 작업 | spec | 비고 |
|------|------|------|
| 엔티티→DTO 매핑을 각 Response의 `static of()`로 이전 | S8 | 프로젝트 VO 패턴과 일관 |
| `for`+`ArrayList` → `stream().map().toList()` 표준화 | S9 | 빈 결과 `DATA_NOT_FOUND` 공통화 |
| freshfood 중복 조회/매핑 경로 공통화 | S10 | 호출 패턴 정리 |
| JPQL 위치 파라미터 → `@Param` 명명 파라미터 | S10b | 순서 오류 예방(S1 재발 방지) |

**완료 기준:** 리팩터링 전후 응답 동일(Phase 3 테스트로 회귀 검증 권장).
**의존성:** Phase 1 네이밍 정리 완료 후 진행하면 충돌 최소화.

---

## Phase 3 — 품질 안전망 (테스트 · 문서)
**목표:** 이후 변경을 안전하게 만드는 회귀 방어선과 문서를 구축한다.

| 작업 | spec | 비고 |
|------|------|------|
| 서비스 단위 테스트(분류/집계/매핑) | S11 | 우선순위 1 |
| 컨트롤러 슬라이스 테스트(`@WebMvcTest`, 검증/예외) | S11 | 우선순위 2 |
| 리포지토리 `@DataJpaTest` | S11 | 우선순위 3 |
| `springdoc-openapi`로 API 문서 자동화 | S12 | 검증·에러 스키마 노출 |

**완료 기준:** 핵심 서비스 로직 커버, `/swagger-ui` 노출, CI에서 테스트 실행 가능.
**비고:** Phase 2와 병행 가능하나, 가능하면 Phase 2 직전/직후 회귀 검증용으로 확보.

---

## Phase 4 — 운영 준비 (설정 · 보안 · 인프라)
**목표:** 운영 환경에서 안전하고 관측 가능하게 만든다. 변경 폭이 가장 큼.

| 작업 | spec | 비고 |
|------|------|------|
| DB 시크릿 외부화(환경변수/프로파일) | S13 | **보안 우선** — 평문 자격증명 제거 |
| `dev/stage/prod` 프로파일 분리 | S14 | 운영 `show-sql:false`, 풀 튜닝 |
| 캐싱 전략(Spring Cache, 필요 시 Redis) | S15 | read-heavy 예측·지수 데이터 |
| 관측성(actuator·구조적 로깅·correlation id) | S16 | HealthController → actuator 검토 |
| CI/CD·정적분석·커버리지 게이트 | S17 | 파이프라인 구축 |
| (선택) 도메인 타입 안전성 강화 | S18 | `String`→`YearMonth`/enum, 큰 변경 |

**완료 기준:** 운영 프로파일로 기동, 시크릿 비노출, 헬스/메트릭 엔드포인트 동작, CI 게이트 통과.
**의존성:** S13(시크릿)은 가능한 한 빨리(Phase 0~1과 병행해도 무방) 처리 권장 — 보안 사안.

---

## 권장 진행 순서 요약

```
Phase 0  정리·일관화          (저위험, 즉시)
   │
Phase 1  API 계약 일관성       (검증/네이밍/에러)
   │
Phase 2  서비스 슬림화·쿼리정리  (구조 리팩터링)
   │
Phase 3  테스트·문서          (회귀 안전망)
   │
Phase 4  운영 준비            (시크릿/프로파일/캐시/관측/CI)
```

> ⚠️ 예외: **S13(DB 시크릿 평문 노출)** 은 보안 사안이므로 Phase 4를 기다리지 말고
> Phase 0~1 시점에 우선 처리하는 것을 권장합니다.
